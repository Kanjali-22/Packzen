# Dieline Platform Implementation Review

This change implements a three-screen dieline platform in Packzen: a templates gallery, a configuration screen with live dimension updates, and a three-panel editor workspace. The implementation introduces horizontal-net geometry for shipping boxes, blue fold lines, red cut lines, and a dynamic 3D preview that adapts to dimension changes.

The platform flow works: gallery → configure → editor, with template state passing through location.state. Dimension changes in both the configure screen and the editor recalculate geometry and update both 2D and 3D previews. The gallery supports search, filtering by 14 categories, and sorting. The editor uses a three-column layout (properties left, 2D canvas center, 3D preview right) and receives template configuration from the configure screen.

**Watch for:** Geometry correctness issues with the cross-shaped net layout (confirmed: minor flaps missing from side panels), 3D preview camera framing at extreme aspect ratios (likely), missing test coverage for dimension unit conversion (confirmed: no automated tests), and potential performance issues with live preview updates on every keystroke (possible).

**Verdict**: CHANGES_REQUESTED

## High-level view

The geometry engine generates horizontal net layouts for four box styles, positioning body panels in a strip with flaps above and below. The shipping-box layout places four major flaps (above/below front and back panels) but omits minor flaps on the side panels, producing an incomplete cross shape.

Cut lines trace the actual perimeter of the net using line segments, fold lines render as blue dashed lines at panel boundaries, and both systems use a coordinate format supporting horizontal and vertical lines.

The 3D preview normalizes dimensions to a 0–4 range and dynamically centers the camera target on the box's vertical midpoint. Distinct colors differentiate each panel face when rotating. The normalization strategy works for typical box proportions but may produce tiny or oversized boxes at extreme aspect ratios.

DielineConfigurePage and DielineStudio both update previews via React state changes tied to dimension inputs. The configure screen uses `useMemo` to regenerate layout when dimensions change. The editor uses `useEffect` to regenerate layout. Both approaches trigger re-renders, and neither debounces input, potentially causing performance issues with rapid typing.

The template registry defines 12 templates across 5 categories, but the category sidebar lists 15 categories. Nine categories return zero results. Search and filter logic correctly computes counts from the template array—the empty categories are intentional placeholders.

Navigation uses React Router's `navigate` with location.state to pass template configuration from configure screen to editor. The editor reads location.state on mount to initialize dimensions, box style, material thickness, and glue flap width. Returning to the gallery from the editor does not restore the previous filter or search state.

## <details><summary>Issues (7)</summary>

1. **Incomplete flap geometry for shipping-box** — The horizontal layout generates four major flaps (on front and back panels) but omits the four minor flaps that should extend from the side panels. A proper RSC cross-shaped net has eight flaps total. Add the missing flaps to `generateDielineLayout` for `styleId='shipping-box'` and adjust the perimeter cut lines to include the notches.

2. **Extreme aspect ratios may break 3D camera framing** — The normalization divides all dimensions by the maximum dimension, which works for cubes and typical boxes but may produce a tiny box in a huge viewport for very long thin boxes (e.g., 1000×50×50mm). Test and adjust the camera distance or normalization scale factor if needed.

3. **No debouncing on dimension inputs** — Changing a dimension triggers immediate geometry recalculation and canvas redraw on every keystroke. For complex layouts or slow devices, this could cause lag. Consider debouncing dimension state updates or using a separate "apply" button for previews.

4. **Nine placeholder categories with zero templates** — The category sidebar lists 15 categories, but only 5 have templates. The other 9 (Box Inserts, Paper Bags, Window Boxes, Storage Boxes, Sleeves, Envelopes, etc.) return zero results. Either populate these categories or remove them from the sidebar until templates are available.

5. **Unit conversion input validation gap** — Dimension inputs accept any positive number, but converting between units (mm/cm/in) can produce fractional values outside the box style's min/max constraints. The validation logic in `validateDimensions` checks the raw dimension values, not the converted mm values used by the geometry engine. Add validation that checks converted values against box style limits.

6. **Gallery navigation state not preserved when returning from editor** — Clicking "Back to Gallery" from the editor or configure screen navigates to `/dieline` without preserving the previous category filter or search query. Users who filtered to "Mailer Boxes" and opened a template will return to "All" category. Consider using URL query params for filter state or session storage.

7. **No automated test coverage** — The FEAT findings confirm no test command is configured in package.json. Geometry calculations, unit conversion, layout generation, and dimension validation have no automated tests. Critical bugs in these utilities would only surface during manual testing.

## Horizontal net layout and flap geometry

The geometry engine (`dielineGeometry.js`) generates horizontal strip layouts for `shipping-box`, `folding-carton`, `mailer-box`, and `custom-box` styles. For shipping-box, the layout places four body panels side by side (front L×H, side1 W×H, back L×H, side2 W×H) with vertical fold lines between them, plus a glue flap on the right edge.

Four major flaps extend from the front and back panels: `flap1` and `flap2` above, `flap3` and `flap4` below. Each major flap is L wide and W/2 tall. These are the "long" flaps that fold inward from the front and back to close the box.

A standard Regular Slotted Carton (FEFCO 0201) also has four minor flaps extending from the side panels. These are W wide and L/2 tall (half the box length, since the side dimension is the box width). The current implementation omits these four minor flaps. The result is a net that shows only the major flaps, not a complete cross-shaped net.

The cut lines trace the outer perimeter of the net, correctly forming the top and bottom edges around the major flaps. Adding the minor flaps would require extending the perimeter outward at the side panel positions and adding four horizontal notches where the minor flaps meet the strip.



## 3D preview normalization and camera centering

`Dieline3DPreview.jsx` normalizes box dimensions to a 0–4 range by dividing each dimension by the maximum dimension and multiplying by 4. This keeps the longest axis at 4 units. The group scale then adjusts the proportions: the inner `BoxModel` always receives `length: 4`, `width: (W/L)*4`, `height: (H/L)*4`, and the group scale divides each by 4, producing the final normalized dimensions.

The camera is positioned at `[7, 6, 8]` with `fov: 40` and looks at `[0, normalizedDimensions.height/2, 0]`. This centers the camera target on the vertical midpoint of the box, which ensures a cube or typical box is centered in the viewport.

For a very long thin box (1000×50×50mm), the normalization produces length=4, width=0.2, height=0.2. The box will be 4 units long but only 0.2 units tall and wide. At camera distance ~10 units, this appears as a thin line. The camera should either move closer or the normalization should use a different scale factor for extreme aspect ratios.

Each panel face uses a distinct color: side1 uses the flap color, side2 uses the tuck color, end1 uses the dust color, and the bottom, end2, and lid use different colors from the COLORS palette. This makes the box recognizable when rotating.

## Live dimension updates without debouncing

Neither the configure screen nor the editor debounces dimension input changes. Every keystroke triggers `generateDielineLayout`, which recalculates panel positions, fold lines, and cut lines for a 12-panel layout, then updates both the 2D canvas and 3D preview. The canvas uses `requestAnimationFrame` to batch redraws, but the geometry calculation runs synchronously on every state change. On fast devices this is imperceptible; on slower hardware it may cause input lag.

## Template registry and empty categories

The category sidebar lists 15 categories, but only 5 have templates. The other 9 return zero results when selected. The gallery correctly computes counts from the template array and displays them—the empty categories are intentional placeholders for future expansion. From a UX perspective, clicking a category that returns zero results creates friction: users see an empty grid and must click "All" to continue browsing.

## Navigation state loss when returning to gallery

The "Back to Gallery" button navigates to `/dieline` without preserving the user's previous category filter or search query. A user who filtered to "Mailer Boxes" and opened a template will return to the "All" category view. React Router does not automatically preserve query params—the gallery would need to encode filter state in URL query params or use session storage.

## Unit conversion validation gap

When the user changes the unit dropdown from mm to cm, the dimension values are converted and rounded to 2 decimal places. The `<input>` element's `min` and `max` attributes are not updated—they still reference `boxStyle.minDimensions.length` (50mm for shipping-box), but the input now displays the value in cm. A user could type 1cm (10mm), which is below the 50mm minimum. The validation logic checks that dimensions are positive numbers but does not check against box style limits or convert units before validation.
